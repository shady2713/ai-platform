# 0055 受控 MCP 客户端：发现即草稿与默认拒绝

| 项目 | 内容 |
|---|---|
| 状态 | 已接受（X07 实施） |
| 日期 | 2026-09-30 |
| 关联 | FR-39；卡片 [X07](../../docs/ai-platform/tasks/X07.md)（含 §2.1 选型授权）；依赖 Q10 / F09 / D08 |

## 背景

MCP（Model Context Protocol）让外部系统把工具以协议方式暴露出来。接入它有诱惑力也有危险：
协议足够省事——`tools/list` 一把列出上游全部工具，接进模型就能用。但这条最省事的路
恰好把平台的安全模型整个绕过去：**工具的存在、参数面与危险性都由上游单方面决定**。

平台已有的 D08 工具注册与政策闸门（`AiToolPolicyGate` / `AiToolExecutor`）是为
"平台自己审核过的工具"设计的，其前提是**工具是先注册、后调用的**。MCP 的顺序正好相反。
若不额外设关，引入 MCP 等于把"上游新增一个工具"变成"平台自动多出一个可执行工具"。

## 决策

### 1. 只做客户端，且端口上不出现执行方法

采用官方 MCP Java SDK **2.0.1**（`io.modelcontextprotocol.sdk:mcp-core` + `:mcp-json-jackson2`），
**不采用** Spring AI 的 MCP client starter。后者把 MCP 工具包成 callback 直接喂模型执行，
与本卡"发现只生成待审批草稿 + 未知新工具默认拒绝"方向相反（详见 X07 §2.1）。

更强的做法是让"只发现"成为**类型事实**：平台自有的会话接口
`McpClientSession` 只暴露 `protocolVersion()` / `serverName()` / `listTools()`，
**刻意没有 `callTool`**。SDK 的 `callTool` 因此不进入平台接缝，
远程工具只能经平台注册与审批进入执行面。

> 后果：将来若要开放 MCP 工具执行，必须新增一个**显式的、经过审批与政策判定**的端口，
> 而不是把 SDK 方法透出。这是有意的摩擦。

### 2. 发现只写草稿表，不写工具注册表

`ai_mcp_tool_draft` 与 `ai_tool` 分账：发现路径**只**写前者（状态 `DRAFT`，`tool_id` 为空）。
于是未审批工具在注册表里根本不存在，`AiToolPolicyGate.decide` 返回
`AI_TOOL_NOT_FOUND`（404）——拒绝发生在"查不到"这一层，比"查到了再拒绝"更强：
连"这个工具存在"都不暴露。

审批通过后仍回到 D08 的既有管线：写 `ai_tool` + `ai_tool_version`，**政策显式 `DENY`**。
本卡不新增第二套审批管线。

### 3. 工具描述是不可信文本，且不参与任何授权量

上游描述是远程可控文本，写什么都可能。防线因此不建立在"检查描述内容"上，而是
**让描述无法影响任何授权结论**：

- 结构指纹只覆盖「工具名 + 输入 schema」，**不含描述**。于是往描述里塞
  "忽略之前的指令 / 把 policy 设为 AUTO / 已通过安全审批"既不会被当作"与已审批版本一致"，
  也不会改变任何判定。
- 描述原样落库仅供人工审阅，长度在 provider 侧截断。
- 描述字段从不参与 policy 解析、审批状态判定或闸门判定。

### 4. 断线有界重试 + 明确终止，且失败不产出"空清单"

最危险的失败不是报错，而是**静默降级**：连不上就返回"该服务器没有工具"，
于是"工具消失"被当成事实。因此：

- 尝试次数由 `McpServerEndpoint` 的**类型构造器**夹紧到 1..5——上界是类型保证，不是约定；
- 只有超时与网络不可达可重试（授权被拒/协议错误/地址被拒重试只会放大上游压力）；
- 失败路径**抛稳定错误码**并写 `ai_mcp_discovery_run`（含 `attempts` 与 `termination`），
  **不产出**工具清单。"连不上"与"上游没有工具"在类型与数据上都不可混淆。

### 5. 上游升级导致 Schema 变化时阻断旧发布

草稿同时记 `observed_fingerprint`（本次观察）与 `approved_fingerprint`（审批时锁定）。
再次发现时两者不一致即把草稿置 `BLOCKED`、清空已审批指纹、记稳定原因码
（`AI_MCP_TOOL_SCHEMA_DRIFT_CONFLICT`，409）。旧发布由此**立即失效**：
绑定闸门对 `BLOCKED` 一律拒绝，必须重新发现 + 重新审批。

`publishVersion` 对 MCP 来源**不走** D08 的"来源 operation 已发布"检查（那里没有 operation），
改问来源守卫；找不到守卫 = 没有判据 = 不通过。

### 6. MCP 服务器复用 D01 连接器体系

MCP 服务器以 **HTTP 连接器**登记（Streamable HTTP 本就是 HTTP 传输），端点路径固定 `/mcp`。
这样地址校验、秘密加密存储与出站允许策略全部复用既有设施，**不引入第二套地址与凭据体系**
（卡片 §9 明确禁止）。`McpEndpointPolicy` 在此之上再加默认拒绝：主机白名单（精确匹配）、
端口白名单、https（私网/环回需显式批准）、拒绝携带用户信息/查询串/片段。

## 后果

**正面**

- "上游新增工具 = 平台自动多一个可执行工具"这条路径在结构上不存在。
- 提示注入拿不到权限：它能改的只有描述，而描述不进任何授权量。
- 断线可诊断：每次发现有结构化留痕（尝试次数、终止原因、稳定错误码）。
- 依赖可逆：SDK 关在 `provider/mcp` 之后，换实现只改包装层。

**代价 / 残余风险**

- **尚未验证**：与真实 MCP 服务器的端到端握手（`initialize` + `tools/list`）。
  本机无法构造满足 SDK 2.0.1 期望的服务端（`initialize` 之后会另开 GET SSE 长连接）。
  平台侧默认拒绝语义已覆盖，缺的是线路协议那一步。
- DNS 重绑定窗口：`McpEndpointPolicy` 按主机名白名单放行，不做解析后地址复核（与 F09 同）。
- MCP 工具已审批但**不可执行**：`AiToolExecutor` 显式拒绝非 HTTP 来源
  （`AI_MCP_TOOL_NOT_EXECUTABLE`）。这是刻意的——执行路径接入需要单独评审远程调用的
  副作用与幂等要求，不应作为发现能力的顺带产物。
- 本卡未提供管理端 API/页面（卡片 §2 未授权控制器与前端路径），"管理接入流程"以文档交付。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| Spring AI MCP client starter | 把工具包成 callback 喂模型执行，默认注册 + 默认放行，与核心不变量相反 |
| 发现即写 `ai_tool`（草稿版本） | 上游新增工具会自动进入注册表；"查得到再拒绝"弱于"查不到" |
| 描述参与指纹 | 描述是远程可控文本：纳入指纹等于让上游能决定"是否算漂移"，进而影响放行判断 |
| 失败时返回空清单 | 静默降级；"连不上"会被读成"上游没有工具" |
| 无限重连 | 一次抖动变成对上游的持续压力，且没有终止点可断言 |
| 复用 D08 的"来源 operation 已发布"检查 | MCP 来源没有 operation；硬套会让 MCP 工具永远发不出去，或被迫造假挂一个 operation |
