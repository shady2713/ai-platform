# 0051：跨系统主体联邦与授权发现（业务系统 = 接入应用，显式登记 + 独立审批）

日期：2026-09-29。状态：采用（Y01 交付，V2 跨系统链头）。

## 背景

V2 要在**多个业务系统**之间做关联分析（FR-22/23/38）。跨系统必须先回答两个问题，且答案不能
靠猜：

1. 某个外部主体（人）在**哪些系统**里有哪些可访问范围？——用户可能同时是 CRM 与 ERP 的用户，
   但两个系统各自签发自己的用户标识；平台如果"看到同名就当成同一个人"，就会把 A 系统用户的
   权限借给 B 系统的一个人（越权放大），这是一条不可接受的捷径。
2. 这次分析**用哪些系统**？——"全部系统"不是选项：跨系统分析是显式的，且必须能在事后核验
   "当时依据的是哪一份授权事实"。

平台已有的事实来源：应用（`ai_application`，`app_code` 稳定且不可修改）、外部主体
（`ai_subject`，唯一键 `(applicationId, subjectType, externalUserId)`）、资源授权目录
（`ai_resource_grant`）、可信范围解析（A02 `SubjectScopeResolver`）。缺的是"系统"身份的定义与
跨系统身份的**审批事实**。

同时 FR-38 明确：现有的 `app_id` 不能被当作跨企业 tenant_id——它只是应用边界（同一企业也可能
有多个应用；不同企业的应用不能因为编号相邻就被合并）。

## 决策

1. **业务系统 = 接入应用**。`app_code` 是跨系统链里稳定的系统标识（全局唯一、创建后不可修改），
   目录与模型目录都以它命名系统。`appId` 继续只是应用编号，不承担租户语义。
2. **跨系统身份只能显式登记 + 独立审批**（`ai_subject_federation`，V91）：一条映射写清
   "来源应用 + 主体类型 + 外部标识" ↔ "目标应用 + 主体类型 + 外部标识"，先 `PENDING` 提交，
   再由**另一位**操作员批准（`requested_by <> approved_by`）后才是 `APPROVED`。批准时重新核验
   两个应用启用、两个主体 ACTIVE，期间被停用的申请不会获批。撤销（幂等 + 乐观锁 CAS）立即生效；
   撤销后重新提交复用同一行并清空上一次审批痕迹，`revision` 只增不减。
3. **不推断同一身份**：两个应用里 `externalUserId` 相同**不等于**同一个人；映射必须逐对登记。
   映射是**有向**的（A→B 授权 A 侧主体发起、访问 B 侧资源，不等于 B 侧能看见 A）。
4. **授权发现是只读事实，且无权不出现**（`AiSystemCatalogServiceImpl`）：一个系统进入目录的必要
   条件是"应用存在且启用 + 主体在该应用 ACTIVE + A02 范围解析非空 + 至少一条 ACTIVE 授权且动作在
   A03 词表内"；其它系统只能经**已批准**映射进入。无权系统不是被标注为"无权"，而是**不存在**于
   目录与模型目录（`modelCatalog`，JSON，只含系统标识与资源清单，不含外部用户标识）。
   无法认定时返回 `denied=true` 的空目录：同一 `(应用, 外部标识)` 在"未登记"与"已登记但无可用
   系统"两种状态下结果**完全一致**（目录指纹只由身份与条目决定），因此不能借目录枚举主体。
   单系统授权读取用"应用 + 主体类型 + 外部标识 + 状态"四等值条件精确匹配（不用管理端模糊查询），
   并对单系统授权条数设预算：超预算直接拒绝，而不是返回一份"看起来完整"的部分目录。
5. **范围选择是显式、可核验的事实**（`AiAnalysisScopeServiceImpl`）：请求必须给出模式
   （`CURRENT_SYSTEM`/`CROSS_SYSTEM`）、目标系统清单与**看到过的目录指纹**；当前系统必须在目录里，
   目标必须**全部**命中目录（不静默剔除、不静默降级为单系统），跨系统至少包含一个非当前系统。
   选择结果带每个系统的访问指纹与 `selectionFingerprint`；`verify` 用同一份输入重新计算并比对，
   事实（主体、范围、授权、映射版本、目录）变化即 409——**不会**改用"当前仍可访问的系统"。
   核验返回服务端重算结果，调用方携带的 `systems`/`modelCatalog` 不被采信。
6. **本卡不含**：跨系统实体/主数据映射（Y02）、跨源指标口径（Y03）、跨源执行（Y04）、分源权限
   求交（Y05）。Y01 只交付"谁能在哪些系统里看到什么范围"这一层事实，并且不新增任何常驻任务。

## 后果

- 卡片三条验收由此可测：单系统流程不变（无映射时目录只有当前系统，A03 判定照旧）；
  无权系统不出现在目录与模型目录（未批准映射、目标无该主体、目标无授权三种情况都不出现）；
  同 `externalUserId` 跨应用隔离（无映射互不可见；映射有向）。
- 跨系统身份映射的权限独立于应用管理权限：`ai:application:federation`（V91 菜单 4016），
  发现与范围选择复用 `ai:application:query`（只读，不改变授权事实）。
- 撤销路径即时且无需扫描任务：发现每次都重新读库；历史选择在再核验时因指纹变化失败，
  需要重新发现后再选择（用户可感知的 409，而不是静默换目标）。
- 目录按系统标识唯一：同一目标应用出现多条已批准映射时只取编号最小的一条，避免"同一系统两套
  范围"在语义上不可判定（多身份映射到同一系统留给 Y02 之后的语义设计）。
- 新错误码子区间 `1_003_013_xxx`（跨系统）：映射不存在/重复/状态冲突/审批分离/主体不可用、
  目录超预算、范围选择被拒/事实过期。
