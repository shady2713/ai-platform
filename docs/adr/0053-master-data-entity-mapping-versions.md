# ADR 0053：跨系统主数据映射的显式登记与版本固定

- 状态：已接受
- 关联：[Y02 建立跨系统业务对象与主数据映射](ai-platform/tasks/Y02.md)、ADR 0051（跨系统主体联邦）、ADR 0004（DAL 查询入参模式）

## 上下文

跨系统统计要回答"CRM 的客户 C-1001 与 ERP 的客户 E-9001 是不是同一个法人"。这类判断有三种典型做法，
其中两种是错的：

1. **按名称/相似度自动合并**：两家不同公司可能同名，同一个人可能有多种写法。自动合并会把无关数据
   算在一起，而且错误**不可发现**——报表只会"看起来怪"。
2. **按主键/编码直接关联**：两个系统的编号体系互不相关，直接关联等于凭空发明对应关系。
3. **显式登记对应关系**：由有权操作员或可信主数据接口给出"哪个标识对应哪个标识"，平台负责版本化、
   冲突检测与过期判定。工程成本更高，但**可核验、可追责、可回滚**。

同时，跨系统报表/产物是长期存在的：一个季度末生成的报表，必须在半年后按**当时**的对应关系解释，
不能因为映射被修改而改变口径。

## 决策

1. **业务对象是平台侧的"企业统一对象"（`ai_master_object`）**，各系统里的标识通过
   `ai_master_object_mapping` **显式登记**关联；`match_method` 只有人工登记（`MANUAL`）与
   可信主数据接口导入（`TRUSTED_FEED`）两种，两者都必须给出源键。
2. **展示名不参与判定**：`source_name` 只用于页面展示；判定路径按 `(来源系统, 实体类型, 源键)`
   精确匹配。跨系统同名因此**在结构上不可能**被合并（AT-070 第一条）。
3. **映射版本化且发布后不可变**：一个对象的映射按版本组织（`ai_master_object_revision`），草稿可编辑，
   发布时冻结内容指纹（`mapping_fingerprint`）。判定必须显式给出对象标识 + 版本号 + 判定时刻，
   平台**没有**"取最新版本""取服务器当前时间"的省略写法；旧报表按受理时的版本解释，
   发布新版本不改旧结果（AT-070 第三条）。发布是独立审核动作：发布人必须不同于草稿创建人。
4. **冲突与过期一律阻断**：同一对象在同一系统同一实体类型下多条时间窗重叠（一对多）、
   同一源键在重叠时间窗属于多个对象（多对一）、源键/版本有效期不覆盖判定时刻，发布与判定两侧
   都抛稳定错误码（`AI_MASTER_MAPPING_CONFLICT` / `AI_MASTER_MAPPING_EXPIRED_CONFLICT` /
   `AI_MASTER_OBJECT_REVISION_EXPIRED_CONFLICT`），不排序取第一个、不静默降级（AT-070 第二条）。
   唯一"不报错"的否定结论是**未登记**（`mapped=false`）。
5. **目录发现与 Y01 一致**：可访问系统集合复用 Y01 的授权发现（无权系统不出现、拒绝不可区分、
   预算有界）；送进模型的目录只含对象/系统/实体类型/可用性，**不含源键值**（键值是业务数据，
   留在服务端参与关联执行）。
6. **生命周期分治**：对象与版本软删除（审计要回答"历史版本里这条标识属于谁"）；
   映射条目是草稿内容行，物理删除（逻辑删除会让唯一键被历史行占住，导致撤销后无法重新登记）。

## 后果

- 跨系统关联的正确性变成**可核验事实**：每条判定结果都带版本号与冻结指纹，可被报表版本、查询计划
  固定下来复现；版本外改动（例如直连数据库改源键）会被重算指纹拦住（409）。
- 运营成本上升：新增对应关系必须显式登记并经第二人发布。这是有意的成本——它换来"错误合并不可能
  静默发生"。
- 判定路径不接受"最新版本"，调用方必须先读对象事实再显式给出版本；接口面因此更大，但语义更硬。
- 跨对象的一致性检查（多对一）在发布时按**时间窗**（任意重叠）判定，比"今天是否生效"更严格：
  未来的重叠也必须在登记时就解决，避免上线后才暴露冲突。
- 与 Y01 的边界：Y01 解决"主体在哪些系统里有哪些范围"（身份联邦），本 ADR 解决"业务实体的标识对应"
  （主数据映射）。两者都遵循"显式登记 + 独立审核 + 只读发现"的同一条安全线。
