# ADR 0054：有界跨源执行与统一结果（Y04）

- 状态：已接受
- 日期：2026-09-30
- 关联需求：FR-23、FR-26、FR-38（跨系统链 AT-070/AT-071）
- 关联任务：[Y04 有界跨源查询执行与统一结果](../ai-platform/tasks/Y04.md)
- 前置：[Y03 跨源指标口径与关联粒度校验](0053-master-data-entity-mapping-versions.md) 之后的第三个跨源环

## 背景

Y03 已经把"**这些来自不同系统的数能不能相加**"变成了可版本化的显式登记：币种、单位、时区、
时间窗口、主键粒度与聚合顺序缺一不可，查询计划必须逐来源钉住数据集版本与映射版本，
多对多扇出一律阻断。Y03 的产出物 `CrossSourceQueryPlan` 是一个**可执行形态**，但它本身不执行任何查询。

剩下的问题是执行侧的三个具体麻烦，而它们都不是"把 SQL 跑出来"这么简单：

1. **扇出**：一笔 100.00 的订单经 2 张发票 × 3 笔回款展开成 6 行，直接关联求和得 600.00。
   要得到正确答案，必须**先在各来源内部按主键粒度聚合**，再把聚合结果关联起来。
2. **算不出来的时候**：预算超限、来源被截断、某个源取不到、各源数据时间不一致——
   每一种都可能悄悄产出一个"看起来对但偏小/偏旧/不完整"的数字。
3. **重试**：跨源执行天然会重试（来源超时、连接抖动），而重试如果重复计入，
   合计会随重试次数线性膨胀，而表面上一切正常。

## 决策

### 决策一：先源内聚合再按版本化实体键关联，绝不拼多表 JOIN

跨源执行逐源取数，来源侧的预聚合 SQL 由 **D06 的 `QueryPlanSqlCompiler` 编译**
（`GROUP BY 实体键 + SUM(金额) + MAX(数据时间)`），再经 **D03 的只读执行器**拉取有界中间结果。
跨源执行**自己不生成 SQL**。

关联键是 `CrossSourceEntityKey = (键值, 映射版本)`。把版本钉进类型里，
使得"不同版本的键类型相同但不相等"，跨版本合并必然撞上
`AI_CROSS_SOURCE_ENTITY_KEY_REVISION_CONFLICT`——不存在"忘了比版本"的路径。
`join` / `requireSingleMappingRevision` 还会在求和**之前**先校验同版本。

**为什么不让跨源路径自己写 SQL**：D03 的 SQL 守卫、只读账号、连接池与超时语义是已经建立的防线。
跨源路径另写一条 SQL 通道，等于绕开这些防线换一个"看起来更直接"的实现。

### 决策二：每源预算越界即**受控结束**，且扣减发生在计入之前

`CrossSourceBudget` 给出每源与全局的行数、字节、并发、超时与时间点偏移上限，每个上限都有服务端硬顶。
`CrossSourceBudgetAccountant.charge` 在把来源金额**并入合计之前**扣减预算，越界即抛
`AI_CROSS_SOURCE_RESULT_TOO_LARGE`。

顺序是承重的：如果先合并再判断，越限的那一刻内存已经被吃掉了——那不是"受控结束"而是"先 OOM 再报错"。
扣减用 CAS 循环，因此并发下多个来源不会同时看到同一份剩余额度。

取数是**有界并发**的：线程池大小即 `maxConcurrentSources`，逐源 `get(单源超时)` 而非整体
`invokeAll`——整体等待会让一个慢来源把整次跨源执行拖到 N 倍超时。超时的来源 `cancel(true)`
后其余继续，已计入的贡献不会因为别人超时而丢失。

行数硬顶比 D03 的 `MAX_ROWS` **少一行**（999）也是承重的：跨源层必须留出一行探测位，
否则 D06 编译进 SQL 的 `LIMIT` 会在跨源层看到结果之前就把结果截到预算值，
"刚好装下"与"被静默截断"于是无法区分。

另外两条独立的受控结束：

- **来源被截断** → `AI_CROSS_SOURCE_RESULT_TRUNCATED_CONFLICT`。这是最危险的一类：
  源内已预聚合的 SUM 被截断后仍然是"合法数字"但偏小，报表上完全看不出来。
- **必需来源失败** → 整体受控结束，并且**重抛上游原始异常**而不是包一层
  `SOURCE_FAILED_CONFLICT`：上游给的往往是 `AI_CONNECTOR_QUERY_FAILED` 这类**可操作**编号
  （对象未授权、连接不可达），包一层会把"该找谁、该改什么"抹掉。跨源侧的信息不丢——
  写进台账（该来源行标 `FAILED`）与执行记录的失败编号。
  **可选**来源失败则写 `MISSING` 并把执行标记为 `PARTIAL`，缺失角色进结果与执行记录——
  "没有回款记录"与"回款金额是 0"在报表上是两件不同的事。

任何受控结束都把执行记录落到 `FAILED` 并带稳定 `failure_code`，"为什么没算出来"因此可查，
而不是只消失在一次异常里。

### 决策三：一致性时间点取各源**最小值**，偏移进结果且可阻断

跨源合计只能解释为"**所有来源都成立的那个时刻**"，也就是各来源 `MAX(数据时间)` 的最小值。
每个来源的 `asOf`、`maxSkewMillis`、预算用量、缺失来源都是**统一结果的一等字段**
（`CrossSourceExecutionResult`），不是日志——它们一旦只进日志，调用方就再也无法判断这个数字能不能用。

偏移超过声明的容忍窗口即 `AI_CROSS_SOURCE_CONSISTENCY_SKEW_CONFLICT`：
那个时刻离任何一个来源都太远，跨源相加失去意义，此时出数等于假装各源同一时刻。

### 决策四：重试幂等靠持久层机制，不靠"重试时小心一点"

这是本卡最重要的一条。三层机制叠在一起，任何一层单独存在都不够：

1. **每来源一行**：`ai_cross_source_execution_source` 的唯一键 `(execution_id, role, deleted)`
   让"一个来源在一次执行里最多贡献一次"成为**数据库不变量**。
2. **覆盖而不是累加**：重取后走带乐观锁的 `overwriteCountedWithVersion`，
   `amount` 是**赋值**，并且 `status` 一并翻回 `COUNTED`
   （不翻的话，"上次 MISSING、这次取到了"的来源会被求和口径永远排除——
   补了数据却补不进合计）。叠加会让合计随重试次数线性膨胀。
3. **合计由已计入行求和**：执行记录的 `total_amount` 来自
   `SELECT ... WHERE status='COUNTED'`，而写入口径与求和口径**分离**。
   因此即使某个来源被重复计入过，合计也与重试次数无关。

`attempt_count` 让"这个来源重试了两次"可观测——不是只看到一个最终数字。
只有**已出完整结果**的 `SUCCEEDED` 与待执行的 `REGISTERED` 不允许原地重跑（重算必须换执行键）；
`PARTIAL`（结果 `usable()` 为 false，本来就是"还没算完"）、`FAILED` 与 `RUNNING` 都允许重跑，
去重交给台账而不是靠拒绝重试。

### 决策五：超容量的数仓接口**拒绝或转登记**，不引入分布式查询集群

`AiCrossSourceCapacityGate` 按"来源数 × 每源行数预算"（唯一能在执行前诚实算出的容量指标）
判定两条出口：拒绝（`AI_CROSS_SOURCE_CAPACITY_EXCEEDED`）或转登记
（落一条 `REGISTERED` 执行记录，等待人工或批量窗口）。

**明确不引入分布式查询集群**：那是另一个数量级的架构承诺（跨节点调度、分布式一致性与新的运维面），
不该由一个"有界执行"卡片顺手引入。本卡把"要不要为此付这个代价"显式交回给决策者。
登记落库而不是丢进内存队列，是因为队列会在重启时丢掉这些请求。

## 被否决的备选

| 备选 | 否决理由 |
|---|---|
| 跨源路径自己拼多表 JOIN | 绕开 D03 的只读守卫与只读账号；且扇出即重复计算（Y03 §3.1） |
| 预算越界时截断后继续算 | 预聚合的 SUM 截断后仍是合法数字但偏小，报表上看不出来 |
| 超容量时"想办法跑完" | 要跑完就得引入分布式查询集群，属另一个数量级的架构承诺 |
| 重试去重用内存 Map 记录"上次加过" | 进程重启即丢；重试跨进程时重复汇总 |
| 合计在内存里累加 | 与重试次数强相关；改成从已计入行求和才与重试次数无关 |
| 把一致性时间点取执行时刻 | 那正是"假装同一时刻"；跨源合计只能解释到各源最小值 |
| 缺失来源按 0 补齐 | "没有回款记录"与"回款金额是 0"在报表上必须能区分（与 Y03 同立场） |

## 后果

**正面**

- 跨源合计有可复核的来源：每个来源的金额、数据时间点、尝试次数、预算用量都在台账里。
- 算不出来的时候有稳定编号，调用方能区分"缩小范围 / 重试 / 联系来源方"。
- 重试幂等是数据库不变量，不依赖任何应用层的自觉。
- 超容量的代价决策显式化，不再由实现细节隐式承担。

**代价与限制**

- 每个来源要单独往返一次，延迟高于单条多表 JOIN。这是扇出安全的代价，不是缺陷。
- `CrossSourceEntityKey` 强制显式提供实体键集合，不提供"按同名字段自动对齐"——
  自动对齐正是 AT-070 里同名不同实体被误合并的入口。
- 容量判据只能用**预估**扇出行数（来源数 × 行数预算）；真实基数要等查询跑完才知道，那时钱已经花了。

**未纳入本卡**

- 来源级重试的调度策略（退避、熔断）由调用方决定；本卡只保证重试不重复汇总。
- Controller 端点与管理端页面：卡片 §5 的必产是执行器、预算控制、统一结构与容量测试，
  不含协议层。没有端点就不加页面（否则是死 UI）。
- 币种换算：Y03 只登记换算规则标识，本卡按"多币种无换算规则禁止求和"的上游结论执行，不做汇率计算。
