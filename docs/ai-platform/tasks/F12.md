## 1. 任务目标与输入

**修一个可证伪的错误归因。** F11 收尾时实测发现：调用方**主动取消**一个出站请求时，
收到的异常是

```
CompletionException(ExternalHttpException: 出站请求失败)   Reason = CONNECT_FAILED
```

根因在 `GuardedExternalHttpClient.mapFailure`：`CancellationException` 不匹配任何既有分支，
落到 fallback，被标成 `CONNECT_FAILED` + "出站请求失败"。

**问题不是"含糊"，是"错误"**：取消是调用方自己的决定，与网络无关，
把它报成**连接失败**会把排查方向直接引到网络/上游，运维会去查根本没问题的东西。
`ExternalHttpException.Reason` 现有 6 个取值
（`TARGET_NOT_ALLOWED` / `PRIVATE_TARGET_DENIED` / `INVALID_REQUEST` / `CONNECT_FAILED` /
`TIMEOUT` / `RESPONSE_TOO_LARGE`）**没有 `CANCELLED`**，所以这个区分目前无处安放。

- 证据：`docs/ai-platform/verification/f11-outbound-streaming-evidence.md`（"已知观察"一节）
- `docs/ai-platform/verification/f09-outbound-http-evidence.md` —— 守卫现有契约

**动手前必读上面两份**，确认现有错误映射的全部分支，别只改一处。

## 2. 允许修改范围

## 3. 逐步实施

1. **给 `ExternalHttpException.Reason` 增加 `CANCELLED` 取值**，并让
   `mapFailure` 把 `CancellationException` 映射成它，消息要说清"已取消"而不是"失败"。
2. **保持取消的传播语义**：调用方取消后**仍然拿不到任何响应**——本卡只改**归因**，
   不改"取消后不给响应"这一既有性质（F11 与 M07 的用例已钉住，别削弱）。
3. **检查 F11 的流式入口**是否也走同一条映射；若流式有独立的取消路径，一并对齐，
   不要让"同步已可区分、流式仍不可区分"。

## 4. 验收与失败分支

- **调用方取消 → 稳定错误码可区分**（新取值），且**不是** `CONNECT_FAILED`、
  **不是** `TIMEOUT`——这两条要分别断言，因为它们都是"看起来合理的错误归因"
- **真正的连接失败仍然映射到 `CONNECT_FAILED`**（反向用例：不得为了让取消可区分
  而把连接失败也改成别的）
- **真正的超时仍然映射到 `TIMEOUT`**（同上）
- **取消后仍不返回任何响应**（F11/M07 既有性质，断言不得删减）
- 错误**消息不得泄漏**请求体、凭据或上游响应内容

**专项必须用反向测试**：每加一个映射分支，就要有一条用例证明**其它分支没有被带偏**。
只测"取消现在能识别了"是不够的——最可能的回归是把 `CONNECT_FAILED` 顺手改掉。
