### 2.1 依赖选型与 pom 授权说明（范围修订，已获用户批准）

原 §2 未包含任何 `pom.xml`，而本卡必须引入一个 MCP 客户端依赖，**无法在不越界的前提下开工**。
按 §2 自身的规定"必须已明确列入本卡，否则先更新任务范围"，此处显式授权**两处、且仅这两处** pom 改动。

**选型：官方 MCP Java SDK 直用，不采用 Spring AI 的 MCP client starter。**

| 项 | 结论 |
|---|---|
| 坐标 | `io.modelcontextprotocol.sdk:mcp-core` + `:mcp-json-jackson2` |
| 版本 | **2.0.1**（GA 稳定线；`1.1.x` 与 `2.0.1` 均在 Maven Central 上核实过） |
| 版本管理 | 在 `basic-framework-dependencies/pom.xml` **新增一个版本属性**并由 `dependencyManagement` 托管，**不得**在模块 pom 里写死版本号 |

**为什么不选 Spring AI 的 MCP client starter**（仓库已用 `spring-ai` 1.1.8，其 BOM 已含
`spring-ai-mcp` / `spring-ai-autoconfigure-mcp-client-*`，看起来更省事）：

1. **方向性不匹配，不是风格偏好。** 本卡逐步实施第 2 条要求工具发现只生成**待审批草稿**、
   仍走平台注册/Schema/权限/执行政策；第 3 条要求未知新工具**默认拒绝**。
   Spring AI 的 MCP client 用途恰恰相反——把 MCP 工具包成 callback 交给模型执行。
   引入它等于把"自动注册 + 默认放行"的生命周期一并继承，与本卡的核心不变量冲突。
2. **本卡对 SDK 的需求面很窄**：建立连接、`tools/list`、取 schema、报告断线与版本变化。
   协议级 SDK 正好覆盖；不需要 Spring 的 autoconfiguration 与 tool-callback 桥接。
3. **沿用仓库既有形状**：`provider/` 下已有 `springai`、`realtime` 两个自封装 provider，
   用平台自己的接口包住第三方 SDK 是同一套做法。
4. **可逆**：SDK 关在 `provider/mcp` 自有接口之后，将来若需要 Spring AI 集成只改包装层。
   反过来用 starter 则一旦依赖其 callback 模型，抽出成本很高。

**授权边界（严格）**：
- 允许：starter-ai 的 `pom.xml` **新增**这两条依赖；dependencies 的 `pom.xml` **新增**版本属性。
- 禁止：改动任何**既有**依赖版本、禁止改父 POM 结构、禁止引入 Spring AI MCP starter、
  禁止顺带升级 Spring AI 或任何传递依赖。
- 传递依赖 `mcp-core` 仅需 slf4j-api / jackson-annotations / reactor-core / jakarta.servlet-api，
  均为本项目 Spring Boot Web 应用已有，不引入新的重型依赖。
- **不引入分布式查询集群、不做服务端 MCP Server**（本卡只做客户端）。

## 3. 逐步实施

先列出本卡实际要创建/修改的文件、对外方法和验收用例，然后按顺序实施：

1. 在当前兼容依赖线验证MCP客户端协议与传输，明确只做客户端。
2. 工具发现生成待审批草稿，每个工具仍走平台注册/Schema/权限/执行政策。
3. 网络地址、授权令牌、超时、版本漂移与未知新工具默认拒绝。

每一步完成后编译或运行相应focused测试；共享接口先由契约确定，禁止消费者各自猜字段。发现本卡大于3个人工作日时，按持久化/服务/协议/页面/验证拆子卡，保留需求编号和完成证据。

## 6. 工程约束

- 不得修改只读源框架；路径均相对另行授权的工作副本。
- 先检查依赖任务的测试证据与公开契约，禁止用临时stub冒充依赖完成。
- 公开契约变更先改权威Schema和样例再改消费者，不能降低校验或覆盖率基线。
- 构造器注入；Controller VO只属于协议层；Service/DAL不反向导入VO；跨模块只用公开CommonApi/DTO。
- 测试使用真实MySQL/Redis Testcontainers或JUnit/Mockito；不得新建H2测试绕过真实约束。
- 复用Vue/TypeScript工作区、请求和反馈规范；禁止新增显式any、v-html、innerHTML和任意脚本渲染。
- 新增typed包必须有真实typecheck、coverage与build，并验证加载/空/失败/失权/销毁状态。
