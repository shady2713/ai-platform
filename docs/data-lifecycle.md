# 数据生命周期与关系策略

机器可读事实源是 [`docs/contracts/data-lifecycle.json`](contracts/data-lifecycle.json)。
`scripts/check-data-lifecycle.mjs` 保证最终 Flyway schema 的每张表和每条物理外键都有唯一登记，并校验手工快照的版本声明、表、逻辑删除列和外键集合。

## 删除策略

| 策略 | 契约 |
|---|---|
| `soft-delete` | 有恢复价值的主数据；默认查询不可见，最终清理前必须定义恢复、唯一键冲突和保留期 |
| `hard-delete` | 会话、验证码、纯关联或文件载荷；删除后不得残留敏感内容 |
| `append-retention` | 日志和事件正文只追加，只由受审计的保留任务分批物理清理 |
| `platform-managed` | Quartz 内部表，只由 Quartz 维护引用和删除顺序 |

新增表必须先选择一种策略。`BaseDO` 只承载通用审计字段；软删除实体显式继承
`SoftDeletableDO`。恢复必须是鉴权且可审计的独立命令，不能用查询参数绕过默认过滤。

## 关系选择

物理外键清单以机器台账为准，其余关系是显式逻辑引用。

1. 同库、低写入、生命周期稳定的强一致关系优先物理 FK，并显式选择
   `RESTRICT` 或 `CASCADE`。
2. 跨模块、高写入、日志快照或需要保留主体标识的关系使用逻辑引用；引用列必须有索引，
   写入前由拥有方校验，并提供孤儿审计和可审计修复。
3. 软删除父表与物理 FK 子表组合时，FK 只保护最终物理清理；软删除命令仍需处理可见性和关联资源。
4. 跨模块同步校验只通过拥有方的 `*-api` 契约完成，不得跨模块访问 Mapper 或共享表实现。

### 评测表（Q04）

| 表 | 策略 | 规则 |
|---|---|---|
| `ai_eval_suite` / `ai_eval_case` | soft-delete | 控制面配置：草稿可编辑，冻结后编辑必须先建新修订；标识/套件内键在**存活行**中唯一，软删除后同一标识可重建 |
| `ai_eval_run` | append-retention | 事实：执行时冻结套件修订与内容摘要（`suite_digest`）与逐例快照（`summary_json`）；只追加，终态一次收敛 |
| `ai_eval_result` | append-retention | 事实：逐例判定、逐条核对结论、样例/结果摘要；**只追加**，人工复核只改复核字段与最终判定（同时更新结果摘要） |

评测夹具是合成数据：套件只允许 `L1_PUBLIC`/`L2_INTERNAL`（服务层拒绝更高分级），
执行器只把稳定值与摘要写进结果（不含提示词与响应正文），规则词表见
`docs/security/ai-eval-fixtures.md`。

## 当前运行规则

- 权限关联、文件配置、字典类型、短信渠道和用户关联由物理 FK 保护。
- 部门负责人、用户部门、层级父节点和角色数据范围使用
  有索引的逻辑引用，并由写入校验、删除保护和每日完整性任务共同约束。
- 保留任务按配置的保留天数和批次上限清理日志、过期短信验证码与已读站内信，并清理超过绝对过期时间的用户会话；执行结果写入 Quartz 任务日志，未读站内信不自动删除。
- 软删除聚合不得长期处于“不可恢复但无限保留”状态；新增软删除表时必须同时交付恢复或最终清理策略。

## AI 中台票据与主体的保留（A06）

- `ai_access_ticket`（访问票据，逻辑删除表）：**失效票据按保留窗口清理**——已撤销或过期超过
  `basic-framework.ai.ticket.cleanup.retention`（默认 24 小时）的票据由 `AiTicketCleanupJob`
  分批逻辑删除；单批条数（`batch-size`）与批次数（`max-batches`）都有上限，任务幂等。
  保留窗口内票据仍可用于审计对账（与访问日志、票据摘要对应）。
- 撤销应用/主体时，其票据与授权**立即**失效（不等待清理任务），清理任务只负责最终删除。
- 外部主体（`ai_subject`）停用不删除：保留外部标识与范围版本用于审计，删除走软删除管理流程。

## AI 中台表策略（F08 冻结，表随实现任务创建）

AI 表尚未创建，本节省略具体表清单，先冻结分类与编号流程，避免实现期各自发明：

- **生命周期分类**：业务运行类表（运行、任务、消息、事件）按**保留期 + 批量清理**处理，不做逻辑删除列；
  配置类表（模型端点、服务草稿、应用与主体、知识库文档元数据）使用**逻辑删除**，纳入
  `docs/contracts/data-lifecycle.json` 的 soft-delete 策略；内容类对象（文件、向量、报告快照）随业务对象级联清理。
- **权限分类**：AI 表全部登记进 `docs/contracts/data-permission-exemptions.json` 或数据权限规则，
  不允许出现"未分类表"；平台托管表（由框架统一维护的审计/日志类）与运行时保护表必须显式标注。
- **迁移编号流程**：AI 表迁移与框架共用同一 Flyway 序列，领取**下一个可用编号**（当前 V47 已用，
  AI 首个建表迁移从 V48 起）；一张任务卡只领一个编号，禁止预占未来编号、禁止修改历史迁移；
  每次新增迁移必须在同一变更内同步 `数据库文件/basic_framework.sql` 快照，否则 contracts 门禁失败。
- **外键与引用**：AI 表之间允许物理外键；跨模块（infra/system）引用一律用逻辑引用 + 索引，
  由业务模块的授权 SPI 校验可见性（见 F06 的文件业务授权）。

### 知识库表（K02）

知识库一条链按"元数据软删除 + 派生数据物理清理"分治：

| 表 | 策略 | 规则 |
|---|---|---|
| `ai_knowledge_base` / `ai_knowledge_document` / `ai_knowledge_document_version` | soft-delete | 历史版本与引用可追溯；标识/来源键在**存活行**中唯一（函数唯一索引），软删除后同一标识可重建 |
| `ai_knowledge_chunk` | hard-delete | 派生数据：随版本重索引或索引代回收物理删除，不保留"已撤销内容仍可检索"的可能 |
| `ai_knowledge_index_generation` | hard-delete | 索引代状态机（BUILDING/ACTIVE/RETIRED/FAILED）走状态列，退役后代与切片由 K07 清理 |

- 文档删除是**两段式**：先置 `DELETING`（立即关闭检索可见性），再由 K07 回收切片与向量；
  期间不接受同一 `sourceKey` 的新入库。
- 版本进入 `READY`/`SUPERSEDED` 后不可修改（文件、指纹、切片都冻结），历史引用因此不会指向被改写的内容。
- 保留策略落在知识库的 `retention_days`：到期清理由 K07 的清理作业执行，本卡只记录策略值。
- 入库任务（`ai_knowledge_ingestion_task`，K03）是软删除的**运行类**行：租约过期由恢复 Job 回队列或按重试上限置
  FAILED，终态行按保留期随文档版本一并清理；同一版本同一任务在存活行中唯一（函数唯一索引），
  因此"重复入库"不会产生第二条任务。
- 删除是**两段式**（K07）：先撤可见性（文档置 `DELETING`，检索侧立即不可见），再由清理 Job
  （`aiKnowledgeCleanupJob`）分步回收——切片行 → 向量点（按 `document_version_id` 过滤）→ 文件引用
  （经 A07 释放，只在最后一个引用释放时才真正删文件）→ 文档/版本行软删除。
  每一步都幂等且按当前状态推进，因此进程崩溃或发布重启后重启即继续，不需要额外进度记录。
- 索引重建（K07）：新一代索引建立并激活后旧代自动退役，**旧代的切片与向量保留**作为回退窗，
  由孤儿检查（`auditOrphans`）报告残留并可按需回收。
